# FinFlow readiness review — 12 October 2026

## Decision

FinFlow has useful finance workflow primitives, but is not yet a substitute for an enterprise finance platform. A good-looking interface, provider smoke tests, and unit tests do not establish reliable unattended finance operations. The appropriate next release is a controlled, single-entity, single-currency pilot with finance reviewers, after staging migrations and the remaining gates below.

## Benchmark and positioning

[Concourse](https://www.concourse.ai/) presents a broader execution layer for finance: connected enterprise data, accounting/FP&A/treasury work, office collaboration, and organizational controls. Its [YC profile](https://www.ycombinator.com/companies/concourse) confirms the company identity. These are public product claims, not capabilities independently tested during this review.

FinFlow offers reconciliation, invoice-to-PO matching, budget-versus-actual commentary, and read-only investigations. The general data library extends investigations to spreadsheets, delimited exports, JSON and text documents without a fixed financial schema. Its useful differentiator can be a clear record from source data through reproducible calculations to human authorization. Connector coverage, enterprise administration, and operating reliability remain bigger gaps than adding more chat features. No Concourse feature-parity or certification claim is justified.

## Defensibility against general-purpose agents

Memory, retrieval, code execution and an attractive chat UI are useful capabilities, but not a durable moat by themselves. A capable analyst with a frontier coding agent can reproduce many one-off analyses. No implementation can guarantee protection from better models or competitors. The defensible proposition is reducing the total operating burden of a recurring finance process: collecting controlled inputs, preserving definitions and evidence, resolving exceptions, obtaining authorized review, delivering the workpaper, and recovering when something fails.

The strongest initial wedge is a repeated monthly close workflow for a clearly defined customer segment, not “answer any financial question for every company.” A customer should keep FinFlow because it reliably saves preparation and review time, retains the team's approved context, and makes the next close easier. Portability and export remain strengths; trapping customer data is not the value proposition.

Build compounding advantages in this order:

1. **Trusted company context:** source versions, period/entity/currency definitions, owners, explicit user preferences and dated prior decisions. Distinguish a user's presentation preference from approved accounting policy. The current memory release provides indexed historical records and personal preferences; a governed company-definition registry remains to be built.
2. **Repeatable evidence:** exact source identities, code/input hashes, reconciliation checks and review decisions. Generated code is reproducible, but its business interpretation still needs testing. Save an approved analysis as a versioned reusable workflow only after fixtures and assertions establish the intended semantics; that promotion workflow is not implemented yet.
3. **Workflow ownership:** reliable source connectors, fresh-data checks, durable scheduled execution, exception assignment and delivery into existing finance tools. These are future work, not features implied by having a chat agent.
4. **Measured refinement:** convert reviewer corrections and failures into labeled regression cases; compare candidate models and harness revisions against a frozen baseline before promotion. Feedback should improve a tested system, not silently rewrite financial policies or train on every generated answer.

Validate the business case with design partners over repeated closes. Record analyst preparation time, reviewer time, exception resolution time, material errors, overrides, successful repeat runs, and cost per completed workpaper. Compare the same tasks against the team's existing process and a capable general-purpose agent with equivalent authorized data. Retention and willingness to pay after that comparison matter more than a demo's visual quality. No customer ROI or retention evidence has been collected in this implementation.

Concourse publicly describes [code-based calculations and financial-stack integrations](https://www.concourse.ai/technology), plus [embedded deployment and accumulating business context](https://www.concourse.ai/how-we-deploy). Those are relevant competitive requirements, not independently verified performance claims.

## Changes in this implementation

- Native Fireworks configuration and schema output, tool calling, reasoning replay, cancellation, and conservative model capability checks. Tenant-scoped environment fallback and database errors that fail closed.
- Exact decimal-to-cent parsing, strict column identity and period validation, rejection of invalid/empty uploads, and source hash verification before execution.
- Reconciliation only accepts permitted candidate pairs with equal amounts; apparent duplicates need source identity evidence. A balance difference cannot be labeled clean.
- AP holds are recomputed at the final queue boundary. Unapproved or missing POs, nonpositive amounts, weak matches, suspected duplicates, and amount exceptions cannot become payable because an earlier model omitted a flag. AP records authorization; it does not transfer funds or establish goods receipt.
- Variance analysis aggregates repeated rows by period, avoids invented business drivers, distinguishes missing observations, and avoids assigning favorable/unfavorable without account semantics.
- Investigation budgets bound time, calls, tokens, and output. Source IDs retain full workflow identity. Financial aggregation must select an unambiguous dataset/source. Partial runs require review rather than appearing approved.
- Atomic database functions for file replacement and final review; private workspaces for new signups; tenant-bound provider pins; compare-and-set launch/resume guards; read-only status polling.
- Public landing page and graphite design tokens, shared navigation, responsive workspace, searchable/paginated workflow list, accessible modal behavior, and visible loading/error/retry states.
- General source parsing with immutable content identity, original rows and explicit bounds; adaptive JavaScript calculations in a QuickJS WASM worker with no host filesystem/network or package installation, bounded CPU/memory/output, and a parent-thread hard timeout.
- Conversation continuations and searchable historical questions/files, plus private editable preferences. History retrieval preserves dates and provenance; prior answers are untrusted context and do not certify a new financial conclusion.

## Supported boundaries

Matching is capped at **2,000,000 source-row pairs** per job. Split larger inputs into aligned entity/account/period slices. This bounds current quadratic matching; it is not an enterprise throughput result. Investigation row loading is bounded, and source cache size has a configured memory budget. Model requests enforce a 256 KiB serialized input ceiling, reducible with `LLM_MAX_INPUT_BYTES`, plus estimated model context/output reserves. Oversized requests fail explicitly. Uploaded file limits do not establish that every file under the limit can be evaluated in a single model context.

The schema does not provide a validated currency/entity/account-type model. Use one entity and USD per workflow; explicit non-USD currency columns are rejected, and USD-style display is not FX conversion. Do not use this version for consolidation, multicurrency reconciliation, tax treatment, or accounting classification without external review. Missing records are not automatically zero. There is no three-way receipt match, supplier-bank verification, or actual payment execution.

General-data analysis preserves source units; it does not inherit the workflow USD convention. Inputs are capped at 20 MiB/file, 10 files/40 MiB combined, 20,000 rows/500,000 cells, 32 tables, and 200 PDF pages. Generated computation is JavaScript only, with 4 MiB selected input, 24 KiB output, 32 MiB QuickJS heap, a 1.5-second interrupt budget and a 5-second parent-worker timeout. Only two computations run concurrently per process; this is not distributed admission control. Scanned/image-only PDFs require upstream OCR. Spreadsheet formulas require cached values. Arbitrary proprietary binaries, network research and package installation are not supported.

Historical search uses PostgreSQL full-text indexes, bounded excerpts and date filters. It does not provide embedding-based semantic recall or guarantee a hit for every paraphrase. Source-content indexing has explicit coverage limits; metadata and question history are separate from raw-file availability. User preferences are private within their current workspace. Automatic memory can be disabled; original questions/files and audit records remain stored. Removing a preference or file is not a complete erasure of all historical excerpts. Define and test retention, legal holds, exports and complete deletion before production deployment.

## Gates before organization deployment

1. **Durable execution:** replace request-lifetime `waitUntil` execution with a durable queue/worker; persist leases, heartbeats, attempt fencing, cancellation, retry policy, and dead-letter recovery. Exercise process death and concurrent resumes. Current request budgets reduce risk but do not solve delivery/recovery.
2. **Identity and tenant operations:** review existing Demo Org memberships, provision organizations explicitly, configure password/email/MFA policy, establish invites and role administration, and verify cross-tenant access at API, database, storage, export, and model configuration boundaries. SSO/SCIM are not implemented.
3. **Financial semantics:** add entity, currency, account basis, signed amount conventions, business calendars, and provenance-preserving line identifiers. Support partial/one-to-many matches only with explicit conservation checks. Require receipts for three-way AP matching.
4. **Model evaluation:** establish labeled reconciliation, AP, FP&A, and investigation cases. Measure false clean/false payable rates, unsupported assertions, citation coverage, abstention, repeated-run stability, and cost/latency across selected Fireworks models. Provider compatibility is not an accuracy score.
5. **Operational controls:** staging rollout, backup/restore drill, load testing by organization size, admission controls/rate limits, structured traces, alerting, retention/deletion policy, secret rotation, dependency review, and independent penetration testing. No security certification is claimed.
6. **Memory quality:** a dated evaluation set spanning five-month-old uploads, renamed vendors, revised budgets, conflicting preferences, unavailable/deleted files, cross-user requests and cross-organization attempts. Measure retrieval recall, correct temporal interpretation, source reopening, unsupported assertions and latency. Require zero observed access-boundary violations and no unqualified reuse of stale financial facts; quantify retrieval accuracy on a representative held-out dataset before promising seamless recall. Synthetic acceptance checks establish specific behavior, not this broader result.

## Rollout

Do not run unattended payment or accounting writes: this version has no such connector. Retain the human review gate, compare output against source totals, and keep incident/recovery ownership explicit.

## Research basis

[Anthropic’s agent engineering guidance](https://www.anthropic.com/engineering/building-effective-agents) favors simple composable workflows and evaluable boundaries. FinFlow therefore keeps money calculations and approval checks in deterministic code while constraining model judgment.

Fireworks documents [function calling](https://docs.fireworks.ai/guides/function-calling), [structured responses](https://docs.fireworks.ai/structured-responses/structured-response-formatting), and [reliability practices](https://docs.fireworks.ai/guides/reliability). This implementation validates model output, rejects truncated answers, carries tool results through the protocol, and bounds retries/deadlines. Current model options were checked against the [recommended model catalog](https://docs.fireworks.ai/guides/recommended-models); pin and reevaluate model versions before rollout.

The visual research used the restrained information hierarchy of [Modern Treasury](https://www.moderntreasury.com/) and [Mercury](https://mercury.com/). FinFlow uses original layout, copy, and illustrative data, with no borrowed customer claims.

[Anthropic's context engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) supports retrieving relevant durable state into a bounded working context. [Letta's stateful-agent architecture](https://docs.letta.com/v1-sdk/concepts/stateful-agents) distinguishes persistent records from context-window contents. FinFlow applies that separation without adopting either vendor's runtime. [PostgreSQL recommends GIN for full-text search](https://www.postgresql.org/docs/current/textsearch-indexes.html); it provides the initial retrieval index. The [QuickJS binding documentation](https://github.com/justjake/quickjs-emscripten) informs isolation and runtime limits; [Anthropic's sandboxing discussion](https://www.anthropic.com/engineering/claude-code-sandboxing) reinforces constraining generated code's filesystem and network reach. None of these sources certifies this implementation.

## Memory efficiency and evaluation design

Persistent records are the archive, not the prompt. Original uploads, conversation records and execution events remain separately addressable. The interaction ledger records committed business actions with server-generated summaries and original-record pointers; browser navigation is a best-effort observation. It deliberately excludes passwords, request bodies, keystrokes, and unsent drafts. It cannot reconstruct events the previous release never captured. Backfilled records are explicitly distinguished from original events.

Retrieval follows a staged path: scoped indexed search, compact candidate identifiers and excerpts, then opening the relevant source or a focused conversation passage. Source data needed for computation is loaded into the server-side sandbox; only bounded observations and results go to the model. Financial conclusions require reopening current retained evidence and recomputation. Database access checks and memory opt-out apply independently of ranking.

The harness now enforces an aggregate byte budget for automatic recall, ranks preferences against the question instead of loading the latest twenty, and retains a short immediate-parent excerpt with pointers to older turns. Search results are deduplicated and bounded before entering context. Token counts for these caps are conservative estimates, not the model's tokenizer or billed usage. Per-call usage events distinguish provider-reported input/output, cached input when available, latency and phase. Cached input remains part of the run's total token limit.

Fireworks routing uses stable run affinity and an explicit organization cache-isolation key. Static instructions precede variable dates and retrieved context. Fireworks enables prefix caching automatically, but cache hits and their economic benefit depend on the actual provider/model; no hit rate or dollar saving is assumed. No user data or credentials are put into routing identifiers.

Research informing these choices:

- [Anthropic: effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) — small relevant working sets and just-in-time references, rather than an ever-growing transcript.
- [Anthropic: contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval) — preserve source context when indexing, evaluate lexical plus semantic retrieval and reranking. FinFlow currently uses lexical GIN retrieval and date/source filters. Semantic embeddings, learned reranking and a distributed indexing worker are **not implemented**; add them only against a retrieval baseline, not on an unsupported accuracy claim.
- [Anthropic: code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp) — filter and compute outside model context, return useful results, and account for execution isolation/operations. FinFlow uses its own bounded tools and QuickJS worker; it does not claim to implement the MCP architecture.
- [Fireworks: prompt caching](https://docs.fireworks.ai/guides/prompt-caching) — stable prefixes, session affinity, explicit cache isolation and reported cached tokens.
- [LongMemEval, ICLR 2025](https://arxiv.org/abs/2410.10813) — evaluate extraction, reasoning across sessions, time, updates and abstention. Our finance acceptance scenarios borrow these categories; this product has **not** been evaluated on the full benchmark.
- [Anthropic: agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) — assess actual end states and traces, combine deterministic checks with expert review, and run repeated trials.

A release comparison should use a frozen, permissioned finance dataset with varied history lengths, distractor files, revised definitions, exact identifiers, semantic paraphrases and missing evidence. Compare retrieval recall@k and precision@k, answer/citation correctness, stale-fact reuse, abstention, p50/p95 retrieval and end-to-end latency, total and cached tokens, tool calls and provider cost per **correct completed task**. Measure ingestion cost separately. Reject a cheaper model or smaller context that increases false financial conclusions. The small synthetic proofs below are acceptance checks, not statistical evidence for these service levels.
